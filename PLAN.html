Implementation plan

Filing Desk — build plan

Seven phases, in order, each ending at a gate you can check rather than a feeling that it's probably fine. No spec, no code — this is the flow you work through and tick off.

7 phases Gate-driven No dates Stack decided later

Before anything

Four rails that hold for the whole build

These are not phases. They are constraints that apply from the first hour to the last, and every phase below assumes them.

One question is the compass

“How has Apple's long-term debt changed across FY2022–FY2024, and what reason does management give?” Every design argument gets settled by asking whether it moves that question closer to answered.

Cache every byte you fetch

Raw responses go to disk, keyed by URL, never overwritten. You will re-run this hundreds of times. EDGAR is rate-limited and you are not entitled to hammer it.

Ground truth before cleverness

XBRL gives you the reported number for free. Anything your system produces can be checked against it. Build that channel first and you can grade yourself forever after.

Two logs, kept by hand

A decisions log (what you chose, why, what you rejected) and an experiment log (what you changed, what the numbers did). The write-up in Phase 7 is assembled from these, not from memory.

01

Get one number out of one filing

Prove you can reach real data, by hand, before you design a single abstraction around it.

0/0

Everything downstream assumes you can name a company, name a document, and name a number precisely. That sounds trivial and it is not: a filing has a fiscal period that is not a calendar year, a number has a unit and a basis, and the same figure appears restated in a later filing. If you skip this phase you will spend Phase 6 unable to tell a broken tool from a broken agent.

1.1 Learn the shape of the source

Not a tutorial — reconnaissance. You are mapping what EDGAR will and will not give you before you commit to a design.

  • Find how a ticker maps to a CIK, and confirm the mapping is a file you can hold locally rather than a lookup you make every call
  • Fetch one company's submissions record and read it until you can say what a single entry contains: form type, filing date, period of report, accession number, primary document
  • Open the same filing three ways — the index page, the primary HTML document, and the XBRL data — and note what each one is good for
  • Read the access rules: the contact-email header EDGAR requires, and the request rate it expects. Write both down as constraints, not suggestions
  • Put the contact email in an environment file from the very first request. Never in source, not even temporarily

1.2 Pin one number, two independent ways

This is the actual deliverable of the phase.

  • Choose one company, one annual filing, one line item — long-term debt is a good first target because it appears in the statements, the notes, and the narrative
  • Read the number off the document yourself, like a human. Record the value, the units, the period, and where on the page you found it
  • Pull the same number from the structured XBRL data. Record the concept name, the unit, the period type, and the filing it came from
  • Reconcile them. If they differ, find out why before moving on — scaling, a different concept, a restatement, or the wrong period. The reason is more valuable than the match
  • Repeat for one quarterly filing, so you meet duration-vs-instant periods and fiscal-quarter labelling early

1.3 Set up the workbench

Small, boring, and it saves the entire project. Do it now, while there is almost nothing to break.

  • Repo skeleton with a clear split between fetching, deriving, and using — you do not need the final structure, you need the seam between “talks to the network” and “everything else”
  • A cache: every network response written to disk under a key derived from the request, read back on a hit, never silently invalidated
  • Prove the cache works by disconnecting from the network and re-running the same script successfully
  • Pick the universe: 5–10 companies, three years, annual plus quarterly. Prefer one sector so comparisons across companies are meaningful later
  • Start the decisions log with the first four entries: universe, identifier scheme, fiscal-year convention, cache policy

Decisions to record

  • The identifier. What is “a filing” to your system? One string that all four tools will speak. Choose it now — changing it in Phase 4 costs a day.
  • Fiscal convention. Do you label by fiscal year as the company reports it, or by calendar period? Apple's FY ends in September; get this wrong and every comparison is quietly off by a quarter.
  • Universe. Which companies, which forms, which years — and why those.

Done gate

One number, obtained two independent ways, agreeing — and the second run of your script completes with the network off.

Where this goes wrong

Designing the tool interfaces before you have touched the data. You will invent parameters the source cannot support and miss the ones it demands. Also: no cache on day one, which turns every later iteration into a network wait and eventually a rate-limit block.

02

The four tools, as plain functions

No agent, no protocol. Ordinary functions with tests — and the return shapes decided deliberately.

0/0

This is the longest phase and the one that decides whether the project is any good. The craft is not in fetching — it is in what a call gives back. A tool that returns a whole document is a tool that destroys the agent using it. Every return here is designed to be small, to carry a citation, and to offer a way to ask for more.

2.1 Normalise a document once

Three of the four tools read the same underlying text. Turn a filing into a stable, addressable object before you write any of them.

  • Convert the filing to text, preserving enough structure that a heading is still recognisable as a heading
  • Decide what happens to tables — the numbers you care about live in them, and naive text extraction turns a balance sheet into unreadable soup
  • Build a section map: each Item number to its span in the text. Expect the table of contents to fight you, since the headings appear twice
  • Verify the map on several filings from different companies — layouts differ more than you expect — and record how often it fails
  • Store the normalised text and its section map as derived files, so downstream work never re-parses
  • Make every position in the document addressable: section, plus offset. This is the backbone of citations

2.2 list_filings — the cheap one, first

  • Inputs: company, form type, year range. Output: a short list of compact records
  • Each record carries the identifier, form, fiscal period, filing date — enough for an agent to choose, nothing more
  • Cap the number returned and make the cap visible in the response, so nobody is guessing whether the list was complete

2.3 get_fact — the ground-truth channel

The most valuable tool in the set, because it is the one that cannot hallucinate. It also has the most subtleties.

  • Inputs: company, concept, period. Output: value, unit, period, and the filing it was reported in
  • Handle the naming problem — the concept a human says and the concept the taxonomy uses are rarely the same string. Decide whether you map synonyms, or return “not that name, did you mean these” with candidates
  • Handle multiple facts for one period — the same figure reported in the original filing and again in a later one. Decide which you return and say which you returned
  • Never silently coerce units or scale. A wrong unit is worse than a missing value
  • Test against the hand-verified numbers from Phase 1. These become your first golden tests

2.4 search_filing — locate, do not retrieve

  • Inputs: one filing, a query. Output: ranked hit locations, each with a short window of surrounding text
  • Keep it lexical. Honest and explainable beats clever here, and the whole point of the project is that there is no index
  • Return positions and snippets — never sections. The agent decides what is worth reading; that decision is the mechanism you are building
  • Cap the hit count and the snippet size; state both in the response
  • Make “no hits” a useful answer: say what was searched, and suggest the sections most likely to hold that kind of language

2.5 read_section — the budget lives here

  • Inputs: one filing, plus either an Item number or an offset range. Output: text, bounded
  • Set a hard ceiling on the returned size. Item 7 of a large filing is far past any sensible budget, so the ceiling will bite constantly — that is intended
  • When truncated, say so explicitly and return a cursor for continuing. Silent truncation is a bug the agent cannot see and you will chase for hours
  • Reject an unknown Item by listing the Items that do exist in that filing

2.6 Cross-cutting contracts

Decide these once, apply to all four, or you will have four dialects by Phase 4.

  • A single citation shape every tool attaches to every result
  • A single error shape — and errors that are instructions, not stack traces. “That Item does not exist here; available: …” is recoverable. A traceback is not
  • A size discipline: know the typical and worst-case return size of every tool, in characters. Write the numbers down
  • Offline tests built from cached fixtures, so the suite runs with no network
  • Start the eval question list here — every time you manually check something, that is a question with a known answer. Do not wait for Phase 6 to start collecting

Decisions to record

  • Return budget per tool — the number, and the reasoning behind it.
  • Truncation protocol — how the caller learns there is more, and how it asks for it.
  • Concept resolution — synonym mapping versus candidate suggestions.
  • Restatement policy — original filing or latest report, and how the answer discloses which.

Done gate

Sitting at a prompt, calling only these four functions by hand, you can answer the target question — and you have written down the exact sequence of calls you made. That sequence is the trace your agent gets compared against in Phase 4.

Where this goes wrong

Building a fifth tool that “just answers the question” because the four feel awkward. The awkwardness is the signal: fix the return shapes. Second trap: tools that return everything, so the human-play-agent exercise feels easy — it will feel easy right up until a real run floods the context window.

03

Wrap them as an MCP server

The same functions, over the protocol. Project 1 becomes a thing you can hand to someone.

0/0

A thin layer, and yet the phase where a hidden skill shows up: the tool description is the interface. The model never reads your implementation — it reads your name, your description, and your parameter docs, and then guesses. When it guesses wrong, that is your text failing, not the model failing. Finishing this phase also means you have something demonstrable before the agent exists, which is worth a lot if the rest slips.

3.1 Expose, without adding logic

  • Server layer does argument validation, dispatch, and formatting. Nothing else. If you find yourself writing behaviour here, it belongs in Phase 2's functions
  • Schemas with real constraints — enumerate form types, bound year ranges, mark what is required
  • Same citation and error shapes as the plain functions, unchanged

3.2 Write the descriptions as product copy

  • For each tool: what it is for, when to prefer it over its neighbour, what it costs, what it returns
  • State the boundary explicitly — get_fact for a reported figure, search_filing when you need language rather than a number. Overlap is where the model picks wrong
  • Put an example call in the description. It is the cheapest steering there is

3.3 Drive it from a real client

Connect a desktop client and use it as a user would. This is your first honest signal.

  • Ask the target question and watch the sequence of calls, without helping
  • Ask three or four deliberately awkward questions — vague company, wrong year, a figure that is not in a filing at all
  • Every wrong tool choice: change the description, retry, note what changed. This is the first entry in your experiment log
  • Log every call server-side — tool, arguments, bytes returned, duration. You need this instrumentation in place before the agent starts making calls faster than you can read

3.4 Make it installable

  • Install steps someone else can follow without asking you a question
  • Configuration example, with the contact-email requirement called out
  • Sane first-run behaviour on a machine with an empty cache — slow is fine, confusing is not
  • Do the clean-profile test yourself, following only your own written steps

Done gate

From a clean setup, following only the README, the server installs, a client connects, and a multi-filing question gets a correct answer — and you have the server-side log of exactly which calls it took.

Where this goes wrong

Descriptions written for a human reader who already knows the system. Also: quietly adding “helpful” behaviour in the server that the plain functions do not have, so Phase 2's tests stop describing reality.

04

Write the agent loop

Yours, by hand, no framework. Roughly 150 lines and most of the learning in the project.

0/0

The loop is small. What makes it worth writing yourself is that every hard decision in agent engineering shows up in it undisguised: when to stop, what to do with a tool that returned nonsense, how errors get back to the model, what the model is allowed to claim. Use a framework and those decisions are made for you by someone else, invisibly, and you learn nothing you can defend in an interview.

4.1 The skeleton

  • Question in, tool definitions attached, model call, inspect the response
  • If it asked for a tool: execute, append the result in the shape the protocol expects, loop
  • If it answered in text: stop and return
  • Keep the message list as the single source of truth for the run. Resist the urge to keep parallel state early on

4.2 Stopping — decided, not accidental

A loop without deliberate stop conditions is a loop that will spend real money while you watch.

  • Ceilings on iterations, total tokens, and wall-clock time — each one distinct, each one logged when hit
  • Detect the repeat: the same call with the same arguments twice. Decide what happens — refuse and tell it, or serve the cached result with a note
  • Decide what a forced stop returns. A partial answer with citations beats silence, but it must be labelled partial

4.3 Execution and failure handling

  • Validate arguments before executing, and return validation failures as tool results — never as exceptions that kill the run
  • Catch everything at the boundary. An unhandled exception in a tool should end as a message the model can read and route around
  • Write error text that suggests the next move. Compare recovery behaviour between a bare failure and a failure with candidates — this is a real, measurable experiment

4.4 The system prompt as policy

  • State what the tools are for and the preference order between them
  • Require a citation for every figure, and require “not found” over a guess
  • Say explicitly that a number must come from a tool result, never from prior knowledge — the model has read a lot of filings and will happily supply a plausible one
  • Keep it short and version it. When you change it, that is an experiment with a before and an after

4.5 Citations, checked mechanically

  • Collect citations as structured data as tool results come back, not by parsing the final prose
  • After the answer, verify every figure it states appears in some tool result from this same run
  • Failing that check is a first-class outcome, reported and counted — this single check is your cheapest hallucination detector and it will fire more than you expect

4.6 Make every run inspectable

  • Write the full run to a file: question, every message, every call and result, tokens, timings, stop reason
  • One file per run, named so you can find it. You will read hundreds of these
  • Fix the sampling settings and record them, so a difference between two runs is more likely to mean something

Done gate

The target question, answered end to end from the command line, with citations that pass the mechanical check — and you have compared the agent's call sequence against the one you performed by hand in Phase 2 and can explain every difference.

Where this goes wrong

Reaching for a framework the first time the loop misbehaves. Swallowing errors so the run “succeeds” while doing nothing. And accepting a right answer without reading the trace — early on, a correct answer arrived at for a broken reason is the most expensive thing that can happen to you.

05

Memory and context budget

Stop it re-fetching, and stop long runs from drowning in their own transcript.

0/0

A loop that works on a three-call question falls apart on a twelve-call one, and the failure is not obvious — the transcript fills with old filing text, the model loses the thread, and the answer degrades without erroring. Treating the context window as a budget you actively manage is the difference between a demo question and a real one.

5.1 Measure before you fix

  • Instrument context size per turn and cumulative, and record it in the run file
  • Run several multi-filing questions and look at the growth curve — find which tool returns dominate
  • Count duplicate calls across a run. Write the number down; it is your before

5.2 Within-session memory

  • Key results by the call signature, so an identical call is recognised
  • Decide the response to a repeat: return the cached payload again, or a short pointer to where it already sits in the transcript. These behave differently; pick deliberately and note why
  • Keep a running store of established facts — value, unit, period, citation — separate from the message list

5.3 Compaction

  • Set a threshold at which old tool results get summarised and the raw text dropped
  • Hard rule: compaction never drops an established fact or its citation. Those move into the fact store first, then the raw text goes
  • Log every compaction event — what was dropped, what survived, size before and after
  • Test it deliberately with a question long enough to trigger it, and confirm the answer is still right

5.4 Behaviour at the ceiling

  • Decide what happens when the budget is exhausted: compact and continue, or stop and answer with what is held
  • Whichever you choose, the answer says so. A confident answer built on a truncated run is the worst output your system can produce

Done gate

On a question needing eight or more calls: zero duplicate fetches, peak context under your stated ceiling, answer still correct — with the before-and-after numbers in the experiment log.

Where this goes wrong

Compaction that eats the number you already found, so the agent goes and fetches it again — or worse, fills the gap from memory. Also: adding memory before measuring, which leaves you unable to say whether it helped.

06

Evaluation and traces

The phase that turns a demo into an engineering project. Start collecting questions in Phase 2; industrialise here.

0/0

This is the scarcest skill in the field and the reason your repo will not look like the hundred others built on the same public filings. Anyone can show one good answer. Being able to say where your system fails, how often, and what each question costs is a different category of claim — and it is only available to you if you built the measuring apparatus.

6.1 Design the question set

50–100 questions, deliberately tiered so a score tells you something specific rather than an average of unlike things.

  • Tier 1 — single fact. One reported figure, one company, one period. Answer key comes straight from XBRL, so grading is automatic and free
  • Tier 2 — single document, narrative. Requires finding and reading the right section of one filing
  • Tier 3 — multi-filing. Several documents, figures plus narrative. Your target question lives here
  • Tier 4 — traps. Answers that are not in the filings, companies outside the universe, periods not yet filed. Correct behaviour is a clean refusal, and a system that never refuses is broken regardless of its accuracy
  • Keep the distribution honest — do not stack it with Tier 1 to make the headline number look good

6.2 Answer keys

  • Numeric keys derived programmatically from XBRL, with unit and period attached
  • Narrative keys as required elements — the claim that must appear and the citation that must back it — rather than a model answer to match word for word
  • Hand-check a sample of the generated keys. Automated ground truth is only ground truth if you have audited it once

6.3 The scorer

  • Numbers: compare value, unit, and period together. A right number for the wrong period is wrong
  • Set a tolerance and state it — rounding and scaling are real, and pretending otherwise gives you false failures
  • Citation validity as its own score: does the cited location actually contain what was claimed
  • Refusal correctness as its own score, over the Tier 4 questions
  • For narrative grading, a model judge against a written rubric — with a human spot-check of a sample, so you know how far the judge can be trusted

6.4 Metrics worth reporting

  • Accuracy by tier, never a single blended figure
  • Average and worst-case tool calls per question
  • Tokens in and out, and cost per question
  • Latency, median and tail
  • Refusal rate, split into correct refusals and refusals on answerable questions
  • Failure taxonomy with counts — the deliverable the write-up is built on

6.5 Classify failures by cause

The distinction that makes the whole apparatus worth having.

  • Wrong tool chosen — a description problem
  • Right tool, wrong arguments — a schema or naming problem
  • Right data retrieved, wrong conclusion drawn — a reasoning problem
  • Ran out of budget before finishing — a context or efficiency problem
  • Answered without support — a policy and verification problem
  • Tag every failed run by hand until the categories stop changing, then let the counts stand

6.6 Run experiments like experiments

  • One change at a time, whole set re-run, before and after recorded
  • At least three experiments worth writing up — a tool description rewrite, a return-budget change, and memory on versus off are the natural three
  • Keep the ones that did not help. A recorded negative result is the strongest signal in the repo that the numbers are real
  • A trace viewer, however plain, so a failed run can be read end to end without scrolling raw logs

Done gate

A results table regenerated by a single command with nothing hand-edited, plus your three most common failure modes named with counts behind them, plus at least one experiment that made things worse and is written down anyway.

Where this goes wrong

Waiting until the agent is good before starting. It teaches you most while it is still bad — that is when the failure categories are visible. Second trap: quietly tuning against the eval set until the number looks good, which measures your tuning, not your system.

07

Write it up

The part that turns a repo into something worth showing. Assembled from the two logs, not from memory.

0/0

The reader of your repo spends ninety seconds deciding whether you are a person who builds things or a person who follows tutorials. What separates the two is not the code — it is whether you can state your own system's limits in specific numbers. That is the whole point of the previous phase, and this is where it gets cashed in.

7.1 The README

  • Open with the question the system exists to answer, and why it cannot be answered by similarity search
  • The architecture, in one diagram: tools, protocol boundary, loop
  • A real trace, pasted in — the actual calls for the target question, not a cleaned-up illustration
  • The results table, straight from the harness
  • The three failure modes, named, with counts and one example each
  • Cost and latency per question, stated plainly
  • What you would do next, and what you deliberately left out and why

7.2 Make it runnable by a stranger

  • Setup that works from an empty directory, with the contact-email requirement explained rather than assumed
  • An example environment file; the real one never committed
  • Cache and run artefacts excluded from the repo, with a note on what they are
  • One command for the demo question, one for the eval suite
  • Actually clone it fresh into a new directory and follow your own instructions

7.3 The demo

  • A short terminal recording of the target question — tool calls visible, answer with citations at the end
  • Include one failure in the write-up, chosen deliberately. It reads as confidence, not weakness

7.4 Split the story in two

  • Project 1 stands alone: an MCP server someone else can install and point a client at
  • Project 2 stands on top: an agent that answers questions no single document contains
  • Say this explicitly in the README. Two claims land harder than one, and the first is verifiable by the reader in five minutes

Done gate

Someone who has never seen the project clones it, follows the README, and gets a correct cited answer — without asking you anything.

Where this goes wrong

A README that describes ambitions rather than measurements. Every claim in it should be traceable to a number the harness produced.

Before you call it done

Self-test

Out loud, without notes. Anything you cannot answer is unfinished work, not a gap in your presentation.

  • Explain what each of the four tools returns, and why it is that size and not larger
  • Walk through one real trace call by call, and say why the agent chose each tool
  • Name your three most common failure modes and the counts behind them
  • Say what one question costs and how long it takes, median and tail
  • Explain how you tell a retrieval failure apart from a reasoning failure — using the data, not intuition
  • Describe one change you made that made things worse, and how you knew
  • Answer: why is there no vector database in this project?
  • Answer: what breaks first if you go from ten companies to five hundred?
  • Answer: how would you stop it stating a number that never appeared in a tool result?
