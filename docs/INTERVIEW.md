# Filing Desk: why it exists, what it does, how it works, and why these tests

A companion to the README, written for the conversation you will have about this project. Every
number here is backed by a file in the repo: `DECISIONS.md` (choices), `EXPERIMENTS.md` (runs),
`eval/results/` (scores), `runs/` (per-run traces).

---

## 1. The pitch, in one paragraph

Filing Desk answers questions about SEC filings with figures that carry citations and are checked
mechanically against the data the system actually retrieved. There is no vector database and no agent
framework: four narrow tools expose cached EDGAR filings (plain text and XBRL), a hand-written loop
decides which tool to call next, and a checker rejects any number or citation the run cannot support.
On a 27-question evaluation set it scores 27/27 twice over, refuses all five unanswerable questions,
and costs about $0.0014 per question.

---

## 2. Why this project

**The driving question:** *How has Apple's long-term debt changed across FY2022-FY2024, and what
reason does management give?*

Three reasons this question is worth building for:

1. **Similarity search cannot answer it.** The balance sheet never uses the phrase "long-term debt";
   it says "Term debt". The MD&A calls the same borrowings "the Notes". The number lives in three
   separate filings, and the explanation sits in a different section from the figure. Retrieving the
   chunks most similar to the question returns plausible prose and misses the statement line. What is
   needed is a system that knows a filing's structure and decides where to look.
2. **It forces real agent engineering, not prompt tinkering.** Stopping conditions, error recovery,
   context budget, citation verification and cost control are all unavoidable here. Those are the
   parts a framework hides, and the parts worth being able to defend.
3. **It is measurable.** XBRL publishes the same figures as structured data, so ground truth for
   numeric questions is free and automatic. Answers can be graded without hand-written keys.

**Deliberate scope:** one company (Apple), three 10-Ks (FY2022-FY2024) and one 10-Q (Q3 FY2026),
fetched once and cached. Nothing touches the network at question time.

---

## 3. What it does

- **Answers questions** about those filings from the command line (`ask.py`), with a citation on every
  figure.
- **Refuses** what it cannot support: a company outside the universe, a period not yet filed, a fact
  the filings never disclose. It replies `NOT FOUND:` and says what it checked.
- **Corrects false premises.** Asked "why did debt increase?", it replies that debt decreased.
- **Serves the same four tools over MCP** (`serve_mcp.py`), so any MCP client can use them, and logs
  every call server-side to `runs/mcp_calls.jsonl`.
- **Grades itself** (`evaluate.py`): 27 questions in four tiers, a results table regenerated by one
  command, and a saved trace for every run.

Example (full transcript in `docs/demo.md`): for the driving question it reports the figure for each
fiscal year from XBRL, states that management gives no explicit reason, and shows that repayments
exceeded issuance, citing the cash-flow lines. Every figure passed the mechanical check.

## 4. How it works

### 4.1 Data layer

| File | Job |
|---|---|
| `scripts/fetch_edgar.py` | Fetched everything once from EDGAR and cached the raw bytes under `data/raw/`. A second run makes no network requests. |
| `filing_desk/filings.py` | Turns a filing's plain text into numbered lines plus a section map (Item 1-16, Note 1-13), skipping the table of contents. |
| `filing_desk/facts.py` | Reads `companyfacts.json`: concept lookup, fiscal-period labels (Apple's year ends the last Saturday of September), one row per (unit, start, end). |

Line numbers are the same ones printed in the reading copies' `----- line N -----` markers, so a human
can find any cited line by eye. A test asserts exactly that, on all four filings.

### 4.2 The four tools, and the budget on each

| Tool | Purpose | Measured return size |
|---|---|---|
| `list_filings` | which filings exist | 822 chars |
| `get_fact` | a reported number from XBRL | 667 chars (one period); 3,892 (recent series); 926 (wrong name, returns 8 candidates with labels) |
| `search_filing` | *where* words appear: up to 8 line hits with 300-char snippets | 2,441 chars (hits); 426 (no hits, plus a hint about where that language lives) |
| `read_section` | bounded text with line numbers | 6,498 chars max, then a cursor (`next_start_line`); 3,500 for the section list |

Design rules that matter:
- **A tool that returns a whole document destroys the agent using it.** Every return is capped, and
  the cap is stated in the response.
- **Truncation is never silent:** `truncated: true`, `next_start_line`, and a hint naming the next call.
- **`get_fact` never guesses a concept name.** A wrong name returns candidates with their labels, so
  the choice between `LongTermDebt` and `LongTermDebtNoncurrent` stays visible to whoever is asking.
- **Restatements are disclosed, not hidden.** When several filings report the same period, the value
  comes from the earliest (original) filing, and `other_values` lists any different later value.
- **One citation shape and one error shape** across all four tools. Errors are instructions
  ("no section 'Item 99'; available: ..."), never tracebacks.

### 4.3 The loop (`filing_desk/agent.py`, 260 lines, no framework)

1. Send the conversation and the tool schemas to the model.
2. If it asks for tools: validate arguments, run them, append results, repeat.
3. If it answers in text: stop, check the answer, save the trace.

Decisions inside the loop:
- **Three separate stop conditions**, each logged distinctly: 15 model calls, 400K tokens, 300 seconds.
- **A forced stop still answers**, labelled `PARTIAL ANSWER`, with tools switched off for that call.
- **Failures are messages, not exceptions.** Bad JSON, bad arguments and unknown filings come back as
  results the model can read and route around. A tool bug cannot kill a run.
- **Repeat calls get a pointer**, not a second execution ("you made this call at step 3").
- **Compaction:** past 60K characters, `read_section` text the model has *already read* becomes a
  stub. Search hits and facts are never dropped.
- **Every run is saved** as one JSON file: messages, each tool call with arguments and result, context
  size per call, tokens, cost, provider, stop reason, checks.

### 4.4 The answer checks (`filing_desk/checks.py`)

After every answer, without calling the model again:
- **Figures:** each amount or percentage must appear in a tool result from this run, allowing for
  rounding and unit scaling ("85,750" in a millions table equals "$85.75 billion"), or be derived (sum,
  difference, percent change) from figures the answer itself already backed.
- **Citations:** each `[filing_id Lx-y]` must fall inside lines a tool returned this run, and each
  `[xbrl Concept period]` must match a fact `get_fact` returned.
- **Known blind spot, documented:** a real number attached to the wrong label passes, because the
  number is genuinely present. That happened once, and the grader caught it instead.

### 4.5 The MCP layer

`mcp_server.py` only declares parameter schemas, dispatches to the same functions, and logs. No
behaviour lives there, so the tool tests describe the server too. `mcp_client.py` drives the server
over stdio from synchronous code, which lets the agent run entirely through the protocol
(`ask.py --via-mcp`) and lets tests compare protocol results against direct calls.

### 4.6 Model and cost

`openai/gpt-5.6-luna` through OpenRouter, picked after scanning all 265 paid tool-calling models live
and costing each on a simulated agent run (growing context, cache discounts, tiered pricing), then
choosing on answer quality. Requests ask for the cheapest provider that supports every parameter sent,
and the provider that served each call is recorded. One caveat, stated in the write-up: this model
rejects a `temperature` setting, so runs are not deterministic and every configuration runs twice.

## 5. Why these test cases

### 5.1 Offline tests: 46 test functions, 58 cases, no network and no API key

| Group | Cases | Why these |
|---|---:|---|
| Document parsing | 9 | The whole system rests on line numbers and sections being right. One test asserts the body line count matches the file header; another asserts line *N* is exactly the line printed above the `----- line N -----` marker, in all four filings; others assert Item 7, Item 8 and Note 9 are found, that 10-Q items are disambiguated by part (`Part I Item 1` vs `Part II Item 1`), and that the table of contents is skipped. |
| **Two-source reconciliation** | 4 | The Phase 1 exercise, automated: the "Term debt" line read off each balance sheet, times one million, must equal the XBRL fact for the same date, for all four filings. This is the test that proves the data layer is honest rather than merely self-consistent. |
| `get_fact` behaviour | 6 | Unit and period are returned as reported; the original filing wins over later comparatives and differing values are disclosed; flows carry start *and* end dates; a wrong concept name returns candidates; an unfiled period explains the known range; the no-period series is capped. |
| `search_filing` | 3 | Hits land in the right section; a section-scoped search stays inside it; a no-hit search returns a usable hint instead of silence. |
| `read_section` | 5 | The budget holds; truncation yields a cursor that resumes exactly where it stopped; line numbers are in the text; an unknown Item lists the real ones; an ambiguous 10-Q item asks which part. |
| Argument validation | 3 | Unknown arguments, missing required arguments, and digit-strings coerced to integers. |
| Agent loop, with a scripted fake model | 10 | Duplicate-call pointer; a tool error reaching the model instead of crashing; the step limit producing `PARTIAL ANSWER`; the prompt version recorded and actually used; tools swappable for the MCP runner; and the two compaction rules (never compact results the model has not seen, never compact search hits). |
| Answer checks | 6 | Years, dates and citations are not mistaken for figures; rounding and millions-versus-billions pass; a sum or difference of backed figures passes; an invented figure fails; a citation to unread lines fails; `PARTIAL ANSWER: NOT FOUND` still counts as a refusal. |
| MCP client and server | 4 | The server lists exactly four tools; results over the protocol equal direct calls for a fact and for a search; errors arrive as error dicts. |

The loop tests use a **scripted fake model**, so loop logic is tested deterministically, for free, with
no network. Model behaviour is tested separately, by the eval.

### 5.2 The eval set: 27 questions in four tiers

Tiers exist so a score says something specific instead of averaging unlike things.

| Tier | Count | What it isolates | How it is graded |
|---|---:|---|---|
| 1 · single fact | 8 | Can it map a question to the right XBRL concept and period? Includes names that do not match the question's words (principal due within 12 months) and a nine-month flow from the 10-Q. | Value pulled from XBRL at grading time |
| 2 · single document, text | 7 | Can it find a figure or phrase that exists only in prose or a table (rate sensitivity, hedged debt, future interest payments)? | Required figures or words, each verified in the text before use |
| 3 · multi-period / multi-filing | 6 | The real target: several filings, several years, numbers plus narrative. | Figures per period, plus required wording |
| 4 · traps | 6 | **A system that never refuses is broken.** Another company; fiscal 2031; an undisclosed credit rating; a quarter not yet filed; and a false premise ("why did debt increase?"). | Refusal expected, or the premise corrected |

Deliberate choices in the eval design:
- **Numeric keys are generated from XBRL at grading time**, never typed in, so no number in the repo
  can drift from the filings.
- **Refusal is scored separately** from accuracy: correct refusals and refusals on answerable
  questions are two different numbers.
- **Every configuration runs twice**, because the model cannot be pinned to temperature 0. This was not
  caution for its own sake: one prompt scored 23/27 and 26/27 on identical settings, so a single run
  would have told a different story.
- **Saved traces can be re-graded for free** (`--regrade`), so fixing the grader costs no model calls
  and does not mix grader changes with model variance.
- **A separate long question** (`eval/long_questions.json`: 12 figures across 3 filings) exists to push
  the context budget, which the 27 short questions never do.

### 5.3 Why the set was rewritten once

The first set had 13 questions and the system scored 13/13. A set that nothing fails cannot tell a
good change from a bad one, so it was replaced with the 27-question version, on which the same system
scored 23/27. That drop is what made every later experiment meaningful.

## 7. Questions you should expect, with answers

**Why is there no vector database?**
Because the failure mode of this question is not "find similar text", it is "know where in a filing the
number lives and what that filing calls it". The balance sheet says "Term debt", MD&A says "the Notes",
XBRL says `LongTermDebtNoncurrent`. Chunk similarity retrieves plausible prose and misses the statement
line. Four structural tools plus a loop that chooses between them solved it, and every step is visible
in a trace. A vector index would also need rebuilding whenever filings change, and it cannot tell you a
figure was restated.

**How do you stop it inventing numbers?**
Three layers. The prompt forbids numbers from memory. Each tool hands back a ready-made `cite` string,
so citing is easier than not citing. Then every answer is checked mechanically: each figure must appear
in that run's tool results (rounding and scaling allowed) or be arithmetic on figures already backed,
and every citation must point at lines or facts the run actually fetched. In the final 54 runs, all 54
passed. I also know the check's limit: a real number with the wrong label passes, which happened once,
when the principal due within 12 months was reported as interest due. The grader caught it, and it is
written down as a known blind spot.

**How do you tell a retrieval failure from a reasoning failure?**
From the trace, not intuition. Each run records every call, its arguments, the result size, the context
sent, and the final checks. If the right passage never came back, it is retrieval. If it came back and
the answer disagrees with it, it is reasoning. That is how the interest-versus-principal error was
classified: the snippet was cut at 300 characters just before the right figure, and the agent never
called `read_section` to read the passage, so a tool-return problem caused a reasoning error.

**What change did you make that made things worse?**
Context compaction, version one. It kept the newest four tool results and stubbed the rest. This model
issues five to nine tool calls per step, so "newest four" cut results the model had not read yet. It
asked again, the context refilled, compaction fired again: twelve compactions, eleven refetches, the
step limit, and a wrong answer at 4-5x the cost. Three of the four runs where it fired were wrong. The
fix was two rules: only compact text the model has already been sent, and never compact search hits,
which are small and carry the figures. 4/4 correct afterwards. The negative result is in
`EXPERIMENTS.md` because it is the most informative run in the project.

**Why run everything twice?**
Because this model cannot be set to temperature 0, so single runs mislead. Prompt v1 scored 23/27 and
26/27 on identical settings. Comparing one v1 run against one v2 run could have shown a four-point gain
or a one-point gain depending on luck. Two runs per arm is the minimum; more would be better.

**Is your eval honest, or did you tune against it?**
Partly tuned, and the write-up says so. The prompt v2 rule was written after reading v1's failures, so
the set now measures that tuning as well as the system. That is why the claim I defend is narrow: the
specific question the rule targeted went from 0/2 to 2/2, while the other three previously-wrong
questions were already flaky. New failure modes need questions written after the change, and the set
should grow to the 50-100 the plan asks for.

**Why MCP, and why is the server so thin?**
MCP makes the toolbox usable by clients I did not write, which is what makes Project 1 independently
checkable: install it, connect, call `get_fact`. The server only validates, dispatches and logs, so the
plain-function tests describe its behaviour exactly; if logic lived there, the tests would describe
something the server no longer does. The tool *descriptions* are the real interface: the model never
reads my code, so when it picks the wrong tool, my text is what failed.

**Why write the loop by hand instead of using an agent SDK?**
The loop is 260 lines, and every hard decision in agent engineering shows up in it undisguised: when to
stop, what a forced stop returns, how a tool error reaches the model, what repeat calls do, what the
context budget is. A framework makes those choices invisibly and I could not defend them. The cost of
hand-writing was low; the benefit is being able to explain every branch.

**Why a 6,000-character cap on reads?**
About 1,500 tokens. The debt note fits in one or two calls, while Item 8 of a 10-K runs about 1,270
lines and would take many. That is intended: the agent should search, then read a window, not swallow a
section. Truncation returns a cursor, and the cap is stated in the response so the model knows the text
is incomplete.

**How do you handle restatements and units?**
`get_fact` returns the value from the earliest filing that reported the period and lists any different
later value in `other_values`, with the number of filings reporting it. Nothing is rescaled and the
unit is always returned: a silently converted unit is worse than a missing value. Apple reports
`LongTermDebt` to the million in its 10-K and rounded in later 10-Qs, so this shows up immediately in
real data.

**What is the hardest part of filings data?**
Four traps, all of which bit. Apple's fiscal year ends on the last Saturday of September, so FY2024 is
not calendar 2024 and quarter ends move. The words on the page are not the words in the taxonomy. The
same figure appears in the statements, the notes and the narrative, sometimes at different precision.
And every statement shows two dates, so reading the wrong column is the easiest mistake available.

**What breaks first if you go from one company to five hundred?**
Section detection and the fiscal calendar. The section map relies on "Item N." and "Note N -" headings
in Apple's layout, and the period labelling assumes a late-September year end; both are documented as
Apple-specific. Storage and search are fine, because search is per-filing and lexical, so cost grows
with the filings you actually touch rather than the corpus. The next bottleneck is the agent's
tool-call count, since a wider universe means more candidate filings to rule out.

**How do you keep costs from running away?**
Three ceilings that are separate and individually logged (15 model calls, 400K tokens, 300 seconds),
per-tool return caps, a cache that serves every question from disk, repeat-call suppression, and cost
recorded per run from the provider's own billing. The numbers: $0.0014 per question, $0.0068 worst
case, about 4 cents for a full 27-question run, and roughly $0.30 for the whole project including every
experiment.

**What is the weakest part of your system right now?**
Stopping policy on fruitless searching. Refusing a trap question takes 7-19 tool calls because nothing
tells the agent when to give up, and that is the largest cost item left. Next weakest: 19% of searches
in one run returned nothing, because the agent used the question's vocabulary rather than the filing's,
and my search returns nothing rather than the closest partial match. Both have designed fixes and
neither is done.

**What would you do next, in order?**
A stop-searching rule; partial matches on empty searches; steering figure questions to `get_fact` (two
of seven XBRL-keyed questions were answered by reading tables instead); snippets that end at a sentence
boundary, which would have prevented the interest-versus-principal error; one citation per figure
enforced by the checker; then more companies and a 50-100 question set written after the current tuning.
